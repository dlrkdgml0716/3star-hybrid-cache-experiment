# Caffeine·Redis 하이브리드 캐시 실험

팀 캡스톤 프로젝트 종료 후 개인적으로 탐구한 **다중 인스턴스의 L1 캐시 정합성 문제**를 설명하기 위한 독립 실험 프로젝트입니다. 원래 팀 프로젝트의 업무 코드, Git 이력, 환경 파일, 사용자 데이터는 포함하지 않습니다. 단순한 테스트 도메인에서 캐시 동작과 측정 방법을 확인할 수 있도록 구성했습니다.

단일 키 구성에서 정상 부하 3회와 구독 중단 1회를 실행한 과거 기록을 보존합니다. **아래 2026-10-09 공개 수치는 현재 구현의 측정값이 아닙니다.** 2026-10-13 변경 후 실제 Redis 통합 검증·정상 부하 1회·구독 중단 1회·소규모 stale probe를 별도로 실행했으며, 새 결과는 로컬 `results/runs/`에 보존했습니다. 각 실행의 조건·원시 결과·코드 해시를 기준으로 해석하세요.

설계 변경의 목적은 **무효화와 겹친 오래된 조회 결과의 재적재 방어와 트랜잭션 경계 처리 보완**입니다.
직렬화·메시지·키·락은 원본 구현 방식과의 일치도를 높이기 위해 맞췄고, 오류 집계는 실험 계측을 보완했습니다.
변경 전체를 성능 최적화로 설명하거나, 변경 전후 부하 수치의 차이를 개선 효과로 해석하지 않습니다.

## 목적과 범위

- 같은 앱을 두 인스턴스로 실행해 Caffeine L1 → Redis L2 → MySQL 조회 구조를 관찰합니다.
- 데이터 수정 후 Redis L2를 제거하고 Pub/Sub으로 각 인스턴스의 L1을 무효화합니다.
- k6로 목표 RPS와 읽기/쓰기 비율을 설정하고 실제 HTTP RPS, 실패율, dropped iterations를 기록합니다.
- stale read, 메시지 발행 → 수신 지연, 구독 중단 중 수신하지 못한 메시지와 재연결 후 stale 잔존을 관찰합니다.
- 핵심 목적은 Pub/Sub 무효화가 적용된 두 인스턴스에서 정상 부하 중 stale read와 메시지 전달을 관찰하고, 구독 중단 시 옛 L1 값이 얼마나 오래 남는지 확인하는 것입니다. 무효화가 없는 구성과의 개선폭은 측정하지 않습니다.

정상적으로 연결된 구독자가 무효화 메시지를 수신하면 해당 L1 항목을 제거하고, 이후 조회는 L2 또는 DB 경로를 다시 거칩니다. 다만 DB 커밋 후 다른 인스턴스의 L1 무효화가 완료되기까지 불일치 구간이 있을 수 있고, 조회와 캐시 적재가 무효화와 겹칠 수도 있습니다. 구독이 끊긴 동안의 Pub/Sub 메시지는 재전달되지 않습니다. 관찰 범위는 **이 구현의 정상 부하 동작과 구독 중단 상황**이며, 모든 읽기가 즉시 최신 값을 반환한다는 보장은 아닙니다.

Java 17, Spring Boot 3.4.5, Gradle 8.14.3을 사용합니다. Caffeine, Spring Data Redis, MySQL JDBC의 버전은 Spring Boot 3.4.5의 의존성 관리 설정을 따릅니다. Redis 7, MySQL 8.0 컨테이너를 사용하며, 실제 실행 버전과 이미지 ID는 각 실행 기록으로 식별합니다.

## 구조와 동작

```text
HTTP → LabController → Spring @Cacheable(sync=true) 프록시
      → CacheManager 어댑터 → HybridCache
          ├─ L1 Caffeine
          ├─ L2 Redis → 로컬 세대가 같을 때 L1 적재
          └─ ItemService.cached() 로더 → ItemRepository → MySQL
               → Redis 세대가 같을 때 Lua로 L2 저장
               → 저장 성공·로컬 세대 일치 시 L1 적재

app-1의 touch(쓰기) → ID 1의 MySQL version 증가 → 트랜잭션 commit 완료
      → app-1의 로컬 세대 증가·L1 제거
      → Lua로 Redis 세대 교체·L2 제거
      → app-1의 로컬 세대 재증가·L1 재제거 → 무효화 메시지 발행
      → app-2가 메시지를 받아 로컬 세대 증가·ID 1의 L1 제거
```

초기 데이터는 ID 1 한 건이며 쓰기마다 정수 version을 1 증가시킵니다. app-1은 ID 1을 수정하고 app-2는 같은 ID를 읽습니다. 정상 부하의 stale 판정은 모든 쓰기의 커밋 시점 구간과 모든 읽기의 캐시 조회 구간·반환 version을 대조합니다. 별도 stale probe는 자신의 쓰기 version을 기준으로 하므로 동시 k6 쓰기와 혼합하지 않습니다. 무효화 메시지의 발행·수신 timestamp 차이는 별도로 메시지 전달 지연을 측정하는 데 사용합니다. 테스트 도메인은 매장·회원·주문 도메인과 독립적입니다.

L1 키는 문자열이며 문자열 해시로 64개 락 중 하나를 선택합니다. 락은 같은 인스턴스의 조회부터 DB 로딩·적재까지
감싸 중복 로딩을 줄입니다. 다른 인스턴스나 DB 쓰기를 잠그지 않으며, 서로 다른 키도 같은 락에 배정될 수 있습니다.
세대 검증은 성공한 무효화와 겹친 늦은 적재를 방어합니다. 이미 읽은 값을 응답하는 요청이나 메시지 전달 전의
기존 L1 조회까지 최신 값으로 바꾸지는 않습니다. DB 커밋과 Redis 작업 사이의 장애도 남습니다.

### 직렬화와 메시지

직렬화는 JVM 메모리의 자바 객체를 저장·전송 가능한 바이트로 바꾸는 과정입니다.
역직렬화는 그 바이트로 새 자바 객체를 복원하는 과정입니다. JSON은 객체를 표현하는 형식 중 하나이며,
JSON을 만든다는 것 자체가 직렬화입니다. 실제 Redis 사용 여부와 별개의 선택입니다.

| 경로 | 이 프로젝트에서 하는 일 |
|---|---|
| L1 Caffeine | 같은 JVM 안의 Item 객체 참조를 보관. JSON 변환 없음 |
| L2 Redis 저장 | Item → JSON 직렬화기의 바이트 → Redis 저장 |
| L2 Redis 조회 | Redis 바이트 → JSON 역직렬화기 → Item 복원 |
| Pub/Sub | 삭제할 키와 발행 시각을 일반 문자열 `키\|시각`으로 전송 |

L2 값은 `RedisValueConfiguration`에 등록한 `GenericJackson2JsonRedisSerializer`로 변환합니다.
일반 Redis 조회에서는 `RedisTemplate`이 직렬화기를 사용하고, Lua 저장에서는 `GenerationFence`가 같은
직렬화기의 `serialize()`로 값과 세대 인자를 바이트로 만들어 전달합니다. Lua의 TTL 인자는 ASCII 숫자입니다.
다른 인스턴스는 Redis에 저장된 데이터를 복원해 같은 내용을 가진 별도 객체를 만듭니다.

초기 구현은 `ObjectMapper.writeValueAsString()`으로 Item을 직접 JSON 문자열로 만들고
`StringRedisTemplate`에 전달했습니다. 이 방식도 실제 Redis를 사용합니다. 현재는 범용 JSON 직렬화기를
사용하도록 맞췄으며, 호출 위치와 타입 처리 설정까지 포함한 변경이므로 바이트 크기·변환 비용이 같다고 가정하지 않습니다.

무효화 메시지 `1|123456`은 JSON이 아닌 일반 문자열입니다. `1`은 삭제할 항목의 키이고 `123456`은
발행 시각의 예시입니다. Item의 데이터나 version은 메시지에 실리지 않습니다. 수신자는 새 값을 저장하는 대신
자기 L1 항목을 제거하고, 이후 요청이 L2 또는 DB에서 다시 읽도록 합니다. L2 값 직렬화와 메시지 형식은 서로 다른 설정입니다.

### 키와 조회 락

키는 캐시 항목을 찾는 식별자입니다. API의 숫자 ID `1L`은 L1에서 문자열 `"1"`로 사용하며,
Redis L2 키는 `cache-lab:items:1`입니다. 키와 저장할 Item 값은 별개입니다.

락은 문자열 자체를 잠그는 방식이 아닙니다. 키로 번호를 계산해 미리 생성한 64개 `Object` 중 하나를 선택합니다.
`private`는 필드 접근 범위를 제한하는 자바 문법이며 별도의 키 종류를 뜻하지 않습니다.

```java
String key = Long.toString(id);
synchronized (loadLocks[(key.hashCode() & Integer.MAX_VALUE) % loadLocks.length]) {
    return load(id, key, loader);
}
```

같은 인스턴스의 같은 키 요청은 같은 락을 선택합니다. 요청 A가 캐시 미스 후 DB 조회·적재를 하는 동안
요청 B가 기다리고, A가 적재를 끝내면 B는 캐시에서 값을 읽을 수 있습니다. 현재 코드는 캐시 히트 경로도 락 안에서 실행합니다.

```text
요청 A: 락 획득 → L1/L2 미스 → DB 조회 → 적재 시도 → 락 해제
요청 B:          대기 ───────────────────────────→ 락 획득 → 캐시 조회
```

락 해제 기준은 `synchronized` 블록의 종료입니다. DB 트랜잭션 종료 시점과 연동한 락이나 분산 락이 아닙니다.
쓰기 무효화는 이 조회 락을 획득하지 않으므로 조회와 무효화는 겹칠 수 있고, 그때의 늦은 적재를 세대 검증으로 방어합니다.
DB가 UPDATE 중 사용하는 행 잠금은 이 자바 락과 별개의 DB 동작입니다.

원본과 맞추기 전에는 `Long.hashCode(id)`를 사용했습니다. 문자열 해시로 바꾼 것은 JVM 내부 락 배정의 변경이며,
Redis 값의 JSON 직렬화 때문은 아닙니다. ID 1만 사용하는 조건에서는 어느 번호를 고르든 같은 키 요청끼리
하나의 락을 공유합니다. 여러 키가 있으면 해시 방식에 따라 서로 같은 락에 배정되는 양상이 달라질 수 있습니다.

### version과 세대의 차이

| 값 | 용도 | 바뀌는 시점 |
|---|---|---|
| Item.version | 반환한 데이터가 어느 쓰기의 결과인지 판정 | DB UPDATE가 1 증가시키고 커밋으로 확정 |
| Redis 세대 | DB 조회 중 공유 캐시 무효화가 끼었는지 검증 | Lua 무효화에서 새 UUID로 교체 |
| 로컬 세대 | L2/DB 조회 중 해당 JVM의 L1 무효화가 끼었는지 검증 | 로컬 무효화에서 증가 |

세대는 조회에 걸린 시간을 측정하는 값이 아니라 적재 허용 여부를 검사하는 표식입니다.
한 항목을 무효화해도 캐시 종류의 세대가 바뀌므로 진행 중인 다른 키 적재도 거부될 수 있습니다.
현재는 ID 1만 사용합니다.

Redis에서는 세대 교체와 키 삭제를 하나의 Lua로, 세대 비교와 저장을 다른 하나의 Lua로 실행합니다.
각 스크립트 안의 Redis 작업 사이에 다른 Redis 명령이 끼어들지 않도록 하기 위한 구성입니다.
이 원자성은 Redis 안의 작업에만 해당하며 MySQL 커밋까지 묶지는 않습니다.
쓰기 인스턴스에서 L1을 두 번 제거하는 것은 첫 제거 이후 Redis 삭제 전에 시작한 오래된 L2 조회도
늦게 L1에 적재되지 않도록 로컬 세대를 다시 바꾸기 위한 처리입니다.

```text
Redis 세대 G1을 읽음 → DB에서 이전 version 조회 중 대기
 → 다른 요청의 쓰기 커밋 → 무효화가 Redis 세대를 G2로 교체
 → 이전 조회가 완료되어 G1으로 저장 시도
 → Lua에서 G1 ≠ G2 확인 → 오래된 값의 L2 저장 거부
```

이는 `fill.rejected`에 기록하는 정상적인 방어 동작입니다. Redis 연결·타임아웃·역직렬화 문제 등으로
세대 자체를 확보하지 못한 경우는 `generation` 오류이며, 두 상황을 구분합니다.
둘 다 해당 DB 결과의 신규 캐시 적재를 생략하지만, 이미 읽은 값은 그 요청에 반환할 수 있습니다.
세대 불일치가 났다고 자동으로 최신 DB 값을 다시 조회하지는 않습니다.

따라서 다음 세 가지는 별개입니다. 조회 락은 인스턴스 내부 중복 로딩을 줄이고,
세대 검증은 늦은 캐시 재적재를 방어하며, version·시각 비교는 실제 반환한 읽기를 사후 판정합니다.
세대 검증을 추가해도 읽기와 커밋의 선후관계를 확정하지 못하는 불확실 표본은 생길 수 있습니다.

| 위치 | 역할 |
|---|---|
| `src/main/java/.../item/` | 테스트 데이터 조회·version 증가, 명시적인 트랜잭션 |
| `src/main/java/.../cache/` | L1/L2, Pub/Sub, 키·발행/수신 시각 기록 |
| `src/main/java/.../api/` | 조회·수정·실험 제어 API |
| `src/test/` | Redis 모킹·H2 단위 테스트와 별도 Redis를 명시한 경우에만 실행하는 Lua 통합 테스트 |
| `k6/load.js` | RPS 부하 생성, 실측 요청 수·비율·지연·실패 기록 |
| `scripts/` | PowerShell 실험 도구와 결과 집계 |
| `compose.yaml`, `infra/init.sql` | 별도 MySQL·Redis, 앱 두 개, 합성 데이터 |
| `results/` | 이 독립 프로젝트의 실행·단계별 검증 기록. 원본 프로젝트의 결과를 가져오지 않음 |

## 빌드와 실행

PowerShell에서 이 폴더로 이동합니다. Java 17, Docker Compose, k6가 필요합니다. macOS/Linux 빌드는 `./gradlew`; 실험 스크립트는 PowerShell 7의 `pwsh`로 실행할 수 있습니다.

```powershell
.\gradlew.bat test
.\gradlew.bat build
docker compose up -d --build
Invoke-RestMethod http://127.0.0.1:8084/actuator/health
Invoke-RestMethod http://127.0.0.1:18084/actuator/health
```

Compose의 DB 계정 정보는 로컬 실험용 예시값입니다. 기존 프로젝트의 DB·Redis에 연결하지 마세요. 앱 포트는 호스트의 127.0.0.1에만 바인딩하며 DB·Redis 포트는 호스트에 노출하지 않습니다.

초기 SQL은 **새 MySQL 볼륨을 처음 만들 때만** 실행되어 ID 1 한 건을 생성합니다. 이후에는 `mysql-single-key-data` 볼륨의 DB 데이터와 version이 유지되며, `docker compose down`도 볼륨을 삭제하지 않습니다. 이 실험은 팀 프로젝트와 별도의 Compose 환경과 볼륨을 사용합니다.

## API

| 메서드·경로 | 기능 |
|---|---|
| GET `/items/1` | L1/L2를 사용하는 읽기. 실험의 읽기 요청은 app-2로 전송 |
| GET `/items/1/db` | DB 직접 읽기. 참조값 확인에 사용 |
| POST `/items/1/touch` | version 1 증가 후 캐시 무효화. 실험의 쓰기 요청은 app-1로 전송 |
| GET `/experiment/metrics` | 프로세스 식별자, TTL, 카운터, 보관된 메시지 이벤트 |
| GET `/experiment/measurements` | 쓰기 커밋·읽기 조회 구간 및 version 이벤트 스냅샷 |
| POST `/experiment/subscription?enabled=false/true` | 앱 프로세스와 L1 캐시는 유지하고 Redis Pub/Sub 메시지 수신만 중지·재개 |
| DELETE `/experiment/cache` | 호출 인스턴스의 ID 1 L1 제거·Redis 세대 변경·ID 1 L2 제거. Pub/Sub 발행 없음 |

인증이 없는 **로컬 실험 전용 API**입니다. 구독 제어·데이터 수정 API를 운영 서비스에 노출하는 설계가 아닙니다.

## 실험

서로 독립적인 실험은 동시에 실행하지 않습니다. 정상 부하와 별도 stale probe도 동시에 실행하지 않습니다. 각 실험을 시작하기 전에 두 인스턴스의 `subscriberListening`이 true인지 확인합니다. 구독 중단 실험은 그 확인 이후 reader의 구독만 끊습니다. 정상 부하 스크립트는 캐시나 DB를 초기화하지 않으므로 직전 실행 상태가 히트율 등에 영향을 줄 수 있습니다.

### 정상 부하

```powershell
.\scripts\Invoke-Load.ps1 -Rps 100 -WriteRatio 0.1 -Duration 30s
```

목표 RPS는 k6 iteration/s이고 iteration당 HTTP 요청은 하나입니다. 실측 HTTP RPS에는 실패 요청 및 종료 대기 영향이 포함될 수 있으며, 성공 처리량·DB 처리량과 다릅니다. 목표 미달, 오류, dropped iterations는 결과와 함께 해석해야 합니다. 읽기/쓰기 선택은 확률적이므로 실측 비율도 저장합니다.

정상 부하 중 app-1의 모든 쓰기는 version과 DB 커밋 전·후 시각을, app-2의 모든 읽기는 반환 version·L1/L2/DB 출처·캐시 조회 시작·끝 시각을 기록합니다. 읽기 시작 전에 더 높은 version의 커밋 완료가 확인되면 `stale`, 다음 version의 커밋이 읽기 구간과 겹칠 수 있으면 `uncertain`, 그 외에는 `fresh`로 분류합니다. 부하 전 DB version과 부하 후 DB version, k6의 읽기·쓰기 요청 수, 이벤트 수가 일치해야 집계를 인정합니다. `stale-summary.json`은 개별 판정과 분모를 함께 보관합니다. 조회 직전에 reader L1을 한 번 준비하며, DB version과 캐시 상태는 리셋하지 않습니다.

커밋 구간은 UPDATE 실행 전체가 아니라 `beforeCommit` 콜백의 기록 시각 `W전`부터 `afterCommit` 콜백의
기록 시각 `W후`까지입니다. 읽기 구간은 `HybridCache.load()` 시작 시각 `R시작`부터 각 반환 경로에서 읽기 이벤트에
넘긴 종료 시각 `R끝`까지이며, 락 대기와 이후 HTTP 응답 전송은 포함하지 않습니다.
반환 version이 `v`이고 더 높은 version이 존재하면 다음 version `v+1`의 기록과 비교합니다.

| 판정 | 조건 |
|---|---|
| stale | `W후 ≤ R시작`: 새 version의 커밋 완료가 읽기 시작보다 앞서거나 같음 |
| uncertain | `W후 > R시작`이고 `W전 ≤ R끝`: 커밋 가능 구간과 읽기 구간이 겹칠 수 있음 |
| fresh | 위 조건에 해당하지 않음. 실행 중 최종 version을 반환한 읽기도 포함 |

반환 version이 실행 전 기준 version보다 낮으면 stale로 분류합니다. 불확실은 세대 조회 오류나 메시지 유실을
뜻하지 않으며, 기록만으로 커밋과 읽기의 선후관계를 확정하지 못한 표본입니다. 모든 판정은 시계의 비교 가능성을 전제로 합니다.

예를 들어 이전 version 7을 반환했고 version 8의 `W전=100`, `W후=110`이라면 다음과 같습니다.
숫자는 관계를 설명하기 위한 시각 예시이며 실제 측정 결과가 아닙니다.

| 읽기 구간 | 판정 | 이유 |
|---|---|---|
| `R시작=120`, `R끝=125` | stale | version 8의 커밋 완료가 기록된 뒤 version 7을 읽음 |
| `R시작=105`, `R끝=115` | uncertain | 실제 커밋이 100~110 중 어디인지 몰라 읽기 시작 전 커밋 여부를 확정 못함 |
| `R시작=80`, `R끝=90` | fresh | 다음 커밋의 전 시각보다 앞서 읽기를 마침 |

여기서 비교하는 것은 **커밋 전후 콜백의 시각과 캐시 읽기 구간**입니다. UPDATE 실행 시작부터의 전체 쓰기 구간이나
메시지 발행·수신 구간을 비교하는 것이 아닙니다. 메시지가 모두 전달돼도 그전에 기존 L1을 읽은 요청은 stale일 수 있습니다.
또한 저장이 거부된 DB 조회도 이전 값을 응답할 수 있으므로, 적재 거부와 최신 응답 보장을 동일시하지 않습니다.

정상 부하의 기준 조건은 목표 **100 RPS·30초·쓰기 선택 확률 10%**입니다. 기본 VU 설정은 `preAllocatedVUs=50`, `maxVUs=200`입니다. 변경 전 공개 3회와 변경 후 로컬 1회는 별도 실행이며, `k6-summary.json`에 적용값·실측 RPS·dropped iterations·HTTP 실패율이 남습니다. 다른 RPS에서의 성능은 측정하지 않았습니다.

한 DB 행에 쓰기가 집중되므로 목표 RPS가 미달할 수 있습니다. 실행 스크립트는 누락 0건, HTTP 실패 0건, 실측 HTTP RPS가 목표의 95% 이상인 경우에만 부하 검증을 통과시키고, 실패한 실행도 `results/runs/`에 기록합니다. 이 기준은 부하 생성 확인용이며 캐시 성능·정합성 보증이 아닙니다.

스크립트 변수는 `LAB_*`입니다. k6의 `-e`는 스크립트 변수이며, OS의 네이티브 `K6_*` 옵션과 구분합니다. 알려진 실행 모드 변경 환경변수를 거부하고 실제 executor/rate도 검사합니다.

### Stale read와 폴링

```powershell
.\scripts\Invoke-StaleProbe.ps1 -Samples 100 -DelaysMs 0,5,10,20,50,100
# 동일 관측 후 최신 값 반환까지의 HTTP 폴링도 기록
.\scripts\Invoke-StaleProbe.ps1 -Samples 100 -Polling
```

관측 순서는 **reader 캐시 준비 → writer 쓰기 응답 → Δ 대기 → reader 한 번 조회**입니다. `observed.version < written.version`이면 stale입니다. 분모는 해당 Δ에서 성공적으로 관측한 읽기 수이며 시도 수·오류 수도 별도 기록합니다. 관측이 없으면 비율은 null입니다.

t0는 쓰기 HTTP 응답을 수신하고 역직렬화한 뒤입니다. actual dispatch delay와 GET RTT를 저장하며, Δ는 서버 캐시 조회 시각을 뜻하지 않습니다. PowerShell 타이머·HTTP 지연 때문에 매우 짧은 불일치 창을 놓칠 수 있습니다. **0건은 완전한 정합성의 증명이 아닙니다.** Δ별 실행 순서·캐시 상태도 결과에 영향을 줍니다.

이 probe는 별도의 단독 실험으로 실행합니다. 다른 쓰기와 섞이면 자신의 쓰기 version만 기준으로 한 결과를 전체 stale 비율로 해석할 수 없습니다. 정상 부하에서 반환된 모든 읽기의 판정은 위의 서버 이벤트 집계를 사용합니다.

HTTP가 성공해도 Redis 오류로 DB 폴백한 실행은 정상 환경 결과로 인정하지 않습니다. probe도 전후 오류 카운터를
`error-summary.json`에 저장하며, Redis·리스너·음수 시각 차이 오류가 증가하면 원시 관측을 보존하고 `failed`로 표시합니다.

폴링 elapsed는 쓰기 응답 이후 최신 값을 반환받는 데 걸린 시간입니다. HTTP·대기·클라이언트 비용이 포함되어 **Pub/Sub 메시지 전송 지연과 다른 지표**입니다. timeout·조회 실패도 원시 기록에 남깁니다.

### Subscriber 중단

```powershell
.\scripts\Invoke-SubscriberFailure.ps1 -DowntimeSeconds 10
# 같은 방법으로 30/60초 조건도 개별 실행
```

reader 앱 프로세스와 Caffeine L1 캐시는 그대로 두고 Redis Pub/Sub 메시지를 받는 Spring 리스너만 중지합니다. Redis L2 접근과 HTTP 요청 처리는 계속됩니다. 앱 프로세스를 종료하거나 네트워크 전체를 끊는 실험과는 다릅니다.

- 캐시 준비 후 구독 중단을 확인하고 k6 부하를 실행합니다.
- writer가 발행 성공으로 기록한 `키|시각`과 reader의 수신 기록을 비교합니다. 같은 키·시각이 중복되면 구분할 수 없으므로 측정을 실패 처리합니다.
- 비율은 **계측 창의 발행 키·시각 표본 중 그 창에서 수신하지 않은 표본 비율**입니다.
- 시간 계측은 구독 중단 응답을 받은 뒤 시작해 재연결 확인 때 끝납니다. 이 구간에는 스냅샷·k6 준비·종료·재연결 확인이 포함되며, 리스너가 실제로 연결을 끊기 시작한 순간부터의 정확한 단절 시간은 아닙니다.
- 부하 종료 후 구독을 복구하고 DB 참조 version과 reader 반환 version을 비교합니다. 이후 쓰기를 멈춰 둡니다.
- 복구 후 보관된 이벤트에서 누락 키·시각의 수신 여부도 확인합니다. 관측 기간 밖에서 영원히 재전달되지 않는다는 실험 증명은 아닙니다.

재시작, 이벤트 버퍼 초과, 관측 실패, 발행 0건은 정상 0% 결과로 대체하지 않습니다. 구독 복구 실패 시 스크립트가 복구를 재시도하며 실패 경고와 수동 복구 경로를 제공합니다.

## 결과 기록과 해석

매 실행은 `results/runs/<UTC 시각>-<고유 ID>/`에 저장합니다.

- `manifest.json`: 실행 조건·환경·소스 SHA-256, 결과 파일 경로와 해시, 종료 상태.
- 원시 카운터·메시지 이벤트 스냅샷과 k6 로그·요약.
- `error-summary.json`: 두 인스턴스의 캐시 Redis 경로 처리 오류(get/generation/put/delete/publish), 잘못된 무효화 메시지, 음수 시각 차이의 실행 전후 카운터 차이. generation은 세대 확보 실패이며 정상적인 세대 불일치에 의한 적재 거부와 구분합니다. 직렬화·역직렬화 실패도 해당 경로 오류에 포함될 수 있습니다. 하나라도 증가하면 실행을 실패로 표시합니다.
- 정상 부하의 각 읽기·쓰기 version 및 시각 구간과 stale/fresh/uncertain 판정. 단독 probe는 reference/observed version, 오류·RTT·실제 dispatch 지연.
- 메시지 delay는 **발행 직전 wall clock timestamp → 원격 listener 진입**입니다. L1 제거 완료 시각도 별도 기록합니다. DB commit→최신 읽기 지연과 다릅니다.
- mean/p95는 해당 writer의 실행 창에서 발행한 키·시각과 매칭된 reader 수신 표본만으로 계산합니다. p95는 nearest-rank이며 시간창이 다른 lifetime 평균을 빼서 만들지 않습니다.
- 메시지 미수신 표본은 delay 계산에서 제외되므로 표본 수·유실 지표와 함께 읽어야 합니다.

원시 실행 폴더는 기본적으로 Git에서 제외합니다. 공개할 실행을 선별해 `results/published/<run-id>/`로 **전체 실행 묶음**을 복사하고 실행 환경·반복 횟수·알려진 한계를 설명합니다. 결과 한 개만 떼어 기존 조건의 결과라고 표시하지 않습니다. 오래된 실험 자료와 새 구현의 결과를 혼합하지 않습니다.

## 커밋 후 무효화 콜백 (2026-10-13)

쓰기 touch()는 @Transactional 메서드 안에서 DB 변경 후 HybridCache.invalidate(id)를 요청합니다.
캐시는 진행 중인 트랜잭션과 동기화 활성 여부를 확인해 afterCommit 콜백으로 실제 L1/L2
무효화·Pub/Sub 발행을 미룹니다. 롤백 시 실행하지 않으며, 트랜잭션이 없으면 즉시 실행합니다.
외부 트랜잭션에 참여하면 touch()가 반환된 시점이 아니라 외부 트랜잭션의 커밋 성공 후 실행합니다.
쓰기 계측도 커밋 콜백에서 기록하므로 롤백을 커밋 성공으로 집계하지 않습니다.

### touch() 본문 종료와 트랜잭션 커밋

`@Transactional`은 Spring이 메서드 호출을 감싸 DB 트랜잭션을 시작·커밋·롤백하도록 합니다.
`ItemService.touch()` 안에 `commit()` 호출이 없는 이유입니다. UPDATE와 SELECT는 트랜잭션 안에서
수행하는 SQL이고, COMMIT은 그 변경을 최종 확정하는 별도 DB 명령입니다. 커밋은 한 번만 수행합니다.

현재 HTTP 쓰기처럼 `touch()`가 새 트랜잭션을 시작하는 호출은 다음 순서입니다.

```text
컨트롤러가 Spring 프록시의 touch() 호출
 → Spring: DB 트랜잭션 시작
 → touch() 본문 실행
     1. repository.touch(id): UPDATE로 version 증가 (아직 미커밋)
     2. 같은 트랜잭션에서 SELECT로 증가한 version 조회
     3. beforeCommit/afterCommit 계측 콜백 등록
     4. cache.invalidate(id): 별도의 afterCommit 무효화 콜백 등록
     5. return updated: touch() 본문 종료, 아직 컨트롤러에 반환하지 않음
 → Spring: beforeCommit 콜백 실행 → W전 기록
 → Spring: 실제 DB COMMIT 한 번 실행 → 변경 최종 확정
 → Spring: afterCommit 콜백 실행
     1. W후와 쓰기 version 기록
     2. 예약한 L1/L2 무효화·Pub/Sub 발행
 → Spring의 트랜잭션 처리 종료 후 컨트롤러에 결과 반환
 → HTTP 응답 전송
```

**본문의 `return`과 프록시를 거쳐 호출자에게 반환되는 시점은 다릅니다.** 본문이 끝난 순간에 이미 커밋하고
나중에 다시 커밋하는 구조가 아닙니다. SELECT에서 새 version을 읽었다는 사실도 커밋 완료를 뜻하지 않습니다.
같은 DB 트랜잭션은 자신의 미커밋 변경을 읽을 수 있고, 이 SELECT 결과는 HTTP 응답과 쓰기 이벤트 기록에 사용합니다.

콜백 등록은 나중에 실행할 코드를 Spring에 맡기는 작업입니다. 등록하는 순간 `beforeCommit()`이나 `afterCommit()`을
실행하지 않습니다. `beforeCommit()`은 UPDATE 시작 시점이 아니라 커밋 절차 중 호출되고,
`afterCommit()`은 DB 커밋이 성공한 뒤 호출됩니다. 현재 콜백은 같은 호출 흐름에서 실행되며 별도 백그라운드 작업이 아닙니다.
롤백되면 변경이 확정되지 않고 `afterCommit`의 쓰기 기록·무효화도 실행하지 않습니다.

외부 `@Transactional` 메서드가 먼저 트랜잭션을 시작했다면 `touch()`는 그 트랜잭션에 참여합니다.
이 경우 `touch()` 호출이 외부 메서드로 반환된 뒤에도 외부 작업이 계속될 수 있고,
커밋과 콜백은 외부 트랜잭션이 커밋되는 시점까지 미뤄집니다. 따라서 무효화 기준은 서비스 본문 종료가 아닌 커밋 성공입니다.

DB 커밋이 끝나도 Redis는 아직 변경되지 않았을 수 있습니다. 캐시 삭제·발행 실패는 이 코드에서 오류로 기록하고
삼키므로 DB 변경을 되돌리지 않습니다. Redis 오류가 있었어도 HTTP 200이 가능해 실험에서는 HTTP 실패와 내부 오류를 따로 검사합니다.

이전 구현은 TransactionTemplate.execute() 반환 뒤 무효화를 호출했습니다. 현재는 무효화 시점을
공통 캐시가 책임지는 구조로 변경했습니다. [검증 결과](results/verification/20261013-after-commit/README.md)를 참고하세요.
과거 부하 결과와 이전 검증 자료는 해당 당시 코드의 결과이며 현재 구현의 성능 수치로 해석하지 않습니다.
콜백은 영속 작업 큐가 아니므로 DB 커밋과 Redis 무효화 사이의 장애·Pub/Sub 유실을 해결하지 않습니다.

## 원본 방식에 맞춘 직렬화·메시지 (2026-10-13)

캐시 값은 `RedisTemplate<String, Object>`와 `GenericJackson2JsonRedisSerializer`로 저장·복원합니다.
JavaTimeModule, 문자열 날짜 표현, NON_FINAL 기본 타입 정보 및 PROPERTY 타입 표현을 사용합니다.
이는 원본 store-service에서 확인한 직렬화 방식과 맞춘 것이며 업무 코드·데이터·설정 파일을 가져온 것은 아닙니다.
실험 Item은 NON_FINAL 설정에서 구체 타입을 복원하도록 record에서 일반 클래스로 변경했습니다.
HTTP 응답의 id/version/value 필드는 동일합니다. Lua의 비교·저장 인자에도 같은 값 직렬화기를 적용하고,
TTL 인자만 ASCII 숫자로 전달합니다. 일반 GET으로 읽은 세대 값과 Lua 비교 인자의 바이트 표현이 일치해야 합니다.

Pub/Sub 본문은 JSON 대신 UTF-8 일반 문자열 `키|epochMicros`입니다. 키만 있는 메시지도 L1을 제거하지만 지연 표본은 만들지 않습니다.
수신 통계 `receivedTotal`은 자기 메시지를 포함한 전체 수신 수입니다. 발신자 정보가 없으므로 원격 수신이라고 표시하지 않습니다.
메시지 ID·origin 필드를 제거했고, 측정 도구는 writer 발행과 reader 수신의 키·시각을 대조합니다.
단일 writer·읽기 전용 reader와 격리된 실험 채널이 전제입니다. reader 발행, 중복 키·시각, 기록 누락 또는
대조되지 않는 수신을 발견하면 유효한 측정으로 처리하지 않습니다. 외부 발신자 식별은 이 프로토콜로 보장하지 않습니다.
재연결 후 대조 결과도 UUID 기반 메시지 식별이 아닌 키·시각 대조입니다.

기존 metrics/측정 JSON과 스키마가 달라 과거 결과를 현재 스크립트 입력으로 혼용하지 않습니다.
과거 결과 파일은 수정하지 않습니다. 새 실험 전 두 앱을 같은 새 버전으로 재시작하고, 기존 절차의
`DELETE /experiment/cache`로 양쪽 실험 키를 초기화해야 합니다. 이전 값과 세대의 직렬화 형식은 호환되지 않습니다.

### 환경·데이터셋 외에 남은 구현 차이

| 항목 | 원본 cache-common / store-service | 공개 실험 |
|---|---|---|
| 캐시 관리·API | 여러 이름의 범용 CacheManager, 일반 조회·로더 조회·evict·clear | items 전용 Spring 어댑터, 로더 조회와 명시적 invalidate |
| 전체 무효화 | 세대 변경, 영역 키 전체 삭제, `*` 메시지 | ID 1 초기화만 제공, 전체 clear·`*` 메시지 미지원 |
| 키·채널 이름 | 캐시명 기반 이름 | 독립 실험용 cache-lab 접두사 |
| 값 처리 | 여러 타입과 Spring null 값 적응 지원 | Item 전용, null 결과 캐싱 미지원, L2 ID 일치 검사 |
| 관측 | Caffeine recordStats, 캐시별 카운터·지연 Timer·오류 로그 | 읽기 version·구간과 커밋 구간, 개별 발행·수신 기록·실험 카운터 |
| 무효화 호출 | Cache.evict, @CacheEvict 및 도메인별 여러 키 제거 | ItemService에서 HybridCache.invalidate 호출 |

이 차이는 환경 때문에 재현 불가능한 사항은 아닙니다. 현재는 단일 항목의 경합·stale 관찰 범위를 유지하기 위해 남아 있습니다.
두 구현 모두 커밋 후 무효화, Redis 세대 기반 적재 검증, 로컬 세대 기반 L1 적재 검증을 사용하지만
전체 API·실행 비용·오류 경로까지 동일하다고 주장하지 않습니다. 여러 키의 연쇄 무효화는 현재 검증 범위에 없습니다.

여기서 null 캐싱은 DB에 없는 항목을 조회한 결과인 `null`도 기억해 다음 요청의 DB 조회를 줄이는 기능입니다.
현재 API는 존재하는 ID 1의 수정·조회만 실험하고, repository는 없는 항목에 대해 null 대신 404 예외를 발생시킵니다.
따라서 현재 실험에는 null 캐싱이 필요하지 않습니다. 여러 캐시 API·전체 삭제를 구현하지 않은 것도 단일 키 실험 범위를
유지하기 위한 선택이며, 해당 기능까지 검증했다고 주장하지 않습니다.

직렬화·메시지 변경 직후의 검증은 [20개 단위 테스트와 빌드 기록](results/verification/20261013-serialization-message/verification.json)으로
보존했습니다. 이후 오류 집계 보완의 22개 단위 테스트와 실제 Redis·앱 실험을 별도로 수행했습니다.
각 검증 폴더는 당시 코드의 결과이며, 최신 검증 상태는 위의 요약을 기준으로 읽습니다.
