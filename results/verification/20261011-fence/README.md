# 재적재 경쟁 검증

이 저장소는 비공개 애플리케이션에서 검토한 캐시 일관성 문제를 독립적인 Item 모델로 재구현한 실험이다.
팀의 업무 코드·설정·Git 이력을 가져오지 않았다. 원본 서비스와 같은 API나 데이터 모델을 사용하지 않는다.

## 검증하는 문제

| 문제 | 통제한 실행 순서 | 기대하는 결과 |
|---|---|---|
| DB → L2 | reader가 DB 옛 값을 읽고 대기 → writer가 변경·커밋에 해당하는 상태 전환 후 무효화 → reader 재개 | 옛 값의 L2 저장 거부, 다음 조회는 최신 DB 값 |
| L2 → L1 | reader가 L2 옛 값을 읽고 대기 → writer 무효화와 reader의 메시지 처리 → reader 재개 | 옛 값의 L1 저장 거부, 다음 조회는 최신 DB 값 |

`HybridCacheRaceTest`는 실제 캐시 클래스 두 개, 실제 Caffeine과 latch를 사용한다. 공유 Redis는 원자적 동작을
모사하는 인메모리 Mockito 테스트 대역이다. DB는 AtomicReference로 읽은 값과 수정된 값을 분리한다.
따라서 이 테스트 자체는 실제 Redis Lua 실행이나 MySQL 격리 수준을 검증하지 않는다.
기존 `ItemServiceTest`는 H2와 Spring 트랜잭션을 사용해 커밋 후 무효화·롤백 시 무효화 없음도 확인한다.

## 해결 원리

DB 로더 실행 전에 Redis의 캐시 종류별 UUID 세대를 읽는다. 무효화는 Lua 안에서 세대 교체와 키 삭제를
실행한다. 적재는 Lua 안에서 세대가 조회 시작 때와 같은지 비교한 후 TTL과 함께 저장한다.
검사와 저장이 별도 명령이면 그 사이에 무효화가 끼어들 수 있으므로 하나의 스크립트로 실행한다.
이 검사는 원격 인스턴스의 무효화에도 적용되며 Pub/Sub 수신 여부에 의존하지 않는다.

세대 키는 TTL을 두지 않는다. 없으면 SET NX로 새 UUID를 생성한다. 초기 상태를 고정 숫자 0으로 재사용하지 않는다.
세대 조회나 조건부 적재가 실패하면 DB 결과를 반환하지만 L1/L2 적재를 생략한다.
다른 키의 변경도 진행 중인 적재를 거부할 수 있는 캐시 종류별 세대 방식이다. 기존의 무관한 키는 삭제하지 않는다.

L1은 로컬 세대를 사용한다. 무효화의 세대 증가·삭제와 적재의 세대 검사·저장을 같은 모니터에서 처리한다.
L2 조회나 DB 로더 실행 동안 이 모니터를 잡지 않으므로 진행 중인 조회와 무효화가 교차할 수 있고,
그 경우 늦은 적재를 거부한다. 별도의 고정 개수 로더 잠금은 동일 키의 로컬 중복 로딩을 줄인다.

Redis 스크립트의 원자적 실행 근거: [Redis programmability](https://redis.io/docs/latest/develop/programmability/).

## 2026-10-11 관측

- 수정 전 `HybridCacheRaceTest`: 3개 중 3개 실패. 두 재적재 경쟁과 세대 확인 실패 시 적재 생략 정책을 재현했다.
- 수정 후 `test`: 실행된 테스트 모두 통과. 상세 수와 파일 해시는 같은 폴더의 `manifest.json`을 참고한다.
- `bootJar`: 성공.
- 실제 Redis 통합 테스트: Docker 엔진 미실행으로 미실행. `GenerationFenceIntegrationTest`는 기본 실행 시 건너뛴다.
- 기존 공개 부하·구독 장애 수치는 방어 로직 추가 전 결과다. 수정 후 동일 부하 실험은 아직 실행하지 않았다.
- 수정 전 로그는 대화 실행 결과로 확인했으며, 수정 전 소스 해시와 별도 XML 묶음은 보존하지 않았다.
  수정 전 결과를 커밋 해시가 고정된 공개 재현 자료로 주장하지 않는다. manifest와 보존한 XML은 수정 후 검증 자료다.

기본 검증:

```powershell
.\gradlew.bat test bootJar
```

Windows 테스트 JVM에서 `Bad address: listen`이 발생해 이번 검증에서는 임시 Gradle init script로
Test 작업의 `java.net.preferIPv4Stack=true`를 지정했다. manifest에 실제 명령을 기록한다.

실제 Lua 검증에는 **실험 앱과 공유하지 않는 폐기 가능한 별도 Redis**를 준비한다. 이 테스트는 localhost만 사용하며
실험 세대 키를 변경·정리한다. 운영 Redis나 실행 중인 실험 앱의 Redis에 연결하지 않는다.

```powershell
# 별도로 준비한 격리 Redis의 포트로 지정
$env:CACHE_TEST_REDIS_PORT = '16379'
try {
    .\gradlew.bat test --tests '*GenerationFenceIntegrationTest' --rerun-tasks
} finally {
    Remove-Item Env:CACHE_TEST_REDIS_PORT
}
```

## 보장하지 않는 것

- 진행 중인 요청의 응답은 읽어 둔 옛 값일 수 있다. 방어 대상은 무효화 이후의 늦은 캐시 저장이다.
- DB 커밋 후 무효화 전에 생긴 장애, Pub/Sub 지연·유실, Redis 실패·복원은 별도 문제다.
- 로더는 현재 DB 상태를 읽는다는 전제다. 무효화 전부터 존재한 DB 스냅샷이나 지연된 복제본까지 해결하지 않는다.
- 단일 Redis 기준이다. Cluster에서는 Lua가 접근하는 키의 hash slot 설계가 필요하다.
- 성능 비용은 아직 측정하지 않았다. 캐시 미스의 세대 조회, Lua 저장·무효화, 로컬 로더 잠금이 추가된다.
- 재적재 경쟁 두 가지의 해결을 전체 stale 0건, 모든 장애의 복구, 강한 정합성과 동일시하지 않는다.

## 경험을 설명할 때

“비공개 프로젝트의 캐시 설계에서 재적재 경쟁을 분석하고, 독립 실험 프로젝트에 같은 제어 원리를 구현해
실행 순서를 통제하는 테스트로 검증했다”는 설명은 가능하다. 본 자료만으로 원본 서비스의 성능 개선 수치,
운영 장애 감소율이나 실제 트래픽에서의 정합성 보장을 주장할 수는 없다.
실서비스에서의 동작은 검증한 전제하의 예상으로 표현하고, 실제 검증과 구분한다.
